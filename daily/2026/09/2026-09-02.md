# Agent 一手情报｜2026-09-02

本轮筛选出 3 条值得归档的新增信息。今天的信号分布在三个层次：Anthropic 在模型层把长时间 Agent 工作、工具使用、失败恢复和缓存成本直接作为 Fable 5.1 的核心能力与经济性指标；Claude Code 在 Harness 层继续把 auto mode、权限边界、后台任务和子 Agent 恢复做成更严格的 runtime policy；Zed 则从持久状态层展示了代码 provenance、稳定锚点和因果历史如何成为多人/多 Agent 协作的基础设施。

## Anthropic — Claude Fable 5.1 / Mythos 5.1

- **Source:** Anthropic
- **Published:** 2026-09-01
- **Topics:** Model, Agentic Coding, Long-Running Agents, Tool Use, Computer Use, Context Economics
- **Priority:** ★★★★★
- **Original:** <https://www.anthropic.com/claude-fable-and-mythos-5-1>

### What changed

Anthropic 发布 Claude Fable 5.1 与 Mythos 5.1，两者使用同一底层模型，但采用不同安全策略与访问范围。Fable 5.1 面向通用可用场景，Anthropic 将其定位为面向 coding、knowledge work 和 long-running agents 的新旗舰模型；Claude Code 中 Fable 5.1 默认使用 High effort。

这次发布对 Agent 场景最重要的变化不是单项 benchmark，而是能力、执行时长和推理经济性同时被产品化：

- 官方明确强调可执行数小时的 multi-app Agent 工作流，能够规划、调用工具、在步骤失败时恢复，并长时间无人值守运行；
- 面向多日 coding session，强调模型能够持续修改、测试并验证自己的工作，包含视觉验证；
- Terminal-Bench 4.0 上 Fable 5.1 为 55.8%，Mythos 5.1 为 60.9%；OSWorld 2.0 partial-credit 为 77.9%，strict 为 41.7%；AutomationBench 为 31.4%；CursorBench 3.2 为 73.4%；
- API 价格为 $10 / Mtok input、$50 / Mtok output，cache read 为 $0.25 / Mtok，比 Fable 5 低 75%；Anthropic 给出的典型 workload 成本下降约 25%，高度 agentic workload 可下降约 45%；
- Cognition 表示在 Devin 中于发布日开始将 Opus 5 流量迁移到 Fable 5.1，理由包括更低的 cost-per-task 与 cache pricing；
- Anthropic 还披露了长时间和 Agentic Safety 评估：prompt injection robustness 提升，但 approval bypass、auto-mode classifier 绕过，以及超长上下文 / multi-agent 审计覆盖仍是继续关注的风险面。

### Technical details

长任务 Agent 的实际成本不仅由单轮 token 单价决定，还高度依赖重复读取长历史、代码、工具结果和系统上下文产生的 cache-read 成本。Fable 5.1 把 cache read 降至 $0.25 / Mtok 后，模型供应商开始直接通过价格结构优化长期 Harness 的运行经济性。

```text
Long-running task
      ↓
large persistent context
      ↓
repeated cache reads + tool loops
      ↓
model capability × cache economics
      ↓
cost per completed Agent task
```

同时，官方不再只描述“更强的 coding model”，而是把 hours-long execution、failure recovery、self-verification、computer use 和 unattended operation 放在同一产品叙事中。这说明 Agent 模型的竞争指标正在从单轮代码生成向完整 task lifecycle 延伸。

### Why it matters

对 Agent Harness 而言，模型选型正在从“单次 benchmark / token price”转向 **完成一个长期任务的总成本、缓存效率、恢复能力与验证能力**。当模型能够稳定运行更长时间，并且缓存读取成本显著下降，Harness 可以使用更丰富的持久上下文、更频繁的验证循环和更长的自治窗口，而不必只靠激进压缩来控制成本。

**Worth reading:** 是。重点看 long-running agent、pricing/cache、agentic safety 和 Devin 等生产场景反馈，而不是只看 benchmark 表格。

## Anthropic — Claude Code 2.1.257 / 2.1.258

- **Source:** Anthropic / Claude Code
- **Published:** 2026-09-01
- **Topics:** Agent Harness, Sandbox, Permissions, Recovery, Background Agents, MCP, Prompt Cache
- **Priority:** ★★★★★
- **Original:** <https://github.com/anthropics/claude-code/releases/tag/v2.1.257>
- **Follow-up:** <https://github.com/anthropics/claude-code/releases/tag/v2.1.258>
- **Status:** Stable

### What changed

Claude Code 2.1.257 是一轮密度很高的 Harness runtime 与安全边界更新，2.1.258 随后修复了 remote / scheduled session 在权限批准重发后的启动问题。

其中最值得关注的改动包括：

- auto mode 新增 **Containment Escape** 规则：云 metadata credential 获取、egress evasion、cross-tenant reach 不再自动批准，除非环境显式声明这些行为属于预期；
- auto mode 首次读取工作目录之外文件时新增一次性确认，并提供 `permissions.blockReadsOutsideWorkingDirectories` 直接阻断；
- `permissions.ask` 在 compound command / subshell 中被绕过的问题得到修复；Bash 的 Read/Edit deny rule 现在也覆盖 `< file` 重定向和 `tac`、`egrep` 等 reader command；
- `/mcp` reconnect / enable 不再绕过 managed MCP allow/deny list 或 `strictPluginOnlyCustomization`；删除 remote MCP server 时会正确处理受管理策略下的 OAuth credential；
- 插件声明的 command、agent、skill、hook 等组件路径如果通过 symlink 指向插件目录之外，现在直接拒绝；`.mcp.json` 如果是 FIFO 或 device-file symlink 会 fail fast；
- 子 Agent 因电脑休眠、连接中断或服务端错误导致流中断时，会自动继续而不是以 incomplete response 结束；
- background session / command / monitor 的停止、更新、旧 binary 回收和 daemon lock 处理进一步收紧，减少后台资源残留与状态漂移；
- `/fork` 改为通过普通 message 传递 worktree briefing，从而保留原 conversation prompt cache；长截图 session 与 advisor-model background request 的 cache miss 也得到修复；
- `claude --resume <session-id> --bg` 在原 session 未运行时继续使用原 ID，而不是静默创建副本；
- 新增 `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`，允许统一覆盖所有 subagent 的模型选择。

### Technical details

这组变化体现出 auto mode 的权限模型正在从简单的“某个命令是否允许执行”升级为带有环境边界与攻击路径意识的 policy layer：

```text
Tool request
    ↓
command / path / MCP policy
    ↓
containment analysis
    ├─ workspace boundary
    ├─ credential boundary
    ├─ network / tenant boundary
    └─ plugin / symlink boundary
    ↓
auto-approve / ask / deny
```

与此同时，后台 Agent 与 subagent 的 failure semantics 更明确：网络中断、进程生命周期、旧 daemon、后台 monitor、session resume 与权限消息都需要由 runtime 负责恢复和清理，不能交给模型通过 prompt 自行推断。

Prompt cache 也开始作为 session architecture 的一部分被保护。`/fork` 不再通过修改 system prompt 注入 worktree briefing，就是为了避免破坏已有缓存；这表明缓存命中率已经影响 Harness 的消息结构设计，而不只是模型 API 的底层优化。

### Why it matters

Claude Code 正在把“自动模式”从便利功能转化为 **有明确 containment boundary 的执行环境**。Agent 能否长时间无人值守，不只取决于工具调用能力，还取决于权限策略是否覆盖 shell 组合语义、文件边界、MCP、插件路径、credential 与网络逃逸等真实攻击面。

同一版本对 subagent continuation、background lifecycle 和 session identity 的修复也说明，长期 Agent 的可靠性越来越依赖 runtime 提供一致的 lifecycle contract：任务可以暂停、恢复、重连、重启和终止，而不会留下不受控进程或丢失执行状态。

**Worth reading:** 是。Release notes 很长，优先阅读 auto mode containment、MCP/policy、subagent recovery、background lifecycle 和 prompt-cache 相关条目。

## Zed — Xanadu Was Waiting for Agents

- **Source:** Zed
- **Published:** 2026-09-01
- **Topics:** Context Engineering, Provenance, Durable State, Multi-Agent, CRDT, Coding Agent
- **Priority:** ★★★★☆
- **Original:** <https://zed.dev/blog/agentic-xanadu>

### What changed

Zed 发布一篇围绕 DeltaDB、代码 provenance 与 Agent 协作的架构文章。它不是普通产品更新，而是在描述一种适合 Agent 原生开发环境的持久状态模型：文件内容、编辑历史、讨论线程和引用关系不再被压成当前快照，而是保持可追踪的因果结构。

文章展示的关键机制包括：

- DeltaDB 中的 fragment 拥有稳定 identity；anchor 引用代码 span 后，即使周围文本继续变化，也能够继续解析到同一逻辑位置；
- 每个 human / agent operation 由 actor identity 与 Lamport timestamp 命名，使并发修改拥有可追踪的因果顺序；
- Git commit hash 命名 immutable project state，DeltaDB 则通过 base commit + delta IDs 命名 Git commit 之间的中间状态；
- CRDT convergence 允许人和多个 Agent 同时修改同一项目并最终收敛；
- thread 被保存为可复制、永久、结构化的历史，而不是最终被 flatten 成文档；
- Agent 可以沿着 provenance 查看某段代码由谁、何时、基于什么上下文修改，也可以把此前 Agent 反复阅读、编辑和引用的文件或 symbol 当作未来任务的 attention landmark；
- 每个 thread 同时对应一个 Git branch，从而保留与现有 Git 工作流的互操作性。

### Technical details

传统 Coding Agent 通常把代码仓库当前快照与聊天历史作为主要上下文：

```text
Current files + transcript
        ↓
LLM reconstructs history
        ↓
reason about why code looks this way
```

DeltaDB 描述的方向是把部分“记忆”变成 runtime 可以直接查询的结构化 provenance：

```text
Code fragment identity
      +
causal edit history
      +
stable anchors
      +
thread / actor metadata
        ↓
Durable project state
        ↓
Agent queries provenance directly
```

这会改变 Context Engineering 的边界。Agent 不必把所有历史重新塞入 prompt，也不必依赖摘要去保存“谁改了什么、为什么关注这里”；这些信息可以由项目状态层持久化，只在需要时检索进入模型上下文。

### Why it matters

当多个 Agent 并行工作时，仅靠 Git branch、worktree 与 conversation memory 很难表达连续的中间状态、代码级引用和因果关系。稳定 anchor、actor-aware delta 与持久 thread 提供了一个更适合长期、多 Agent 开发的 state substrate。

这条路线与近期 Harness 中“Task 成为 runtime object”“context 按职责分层”“orchestration invariant 迁移到 runtime”的趋势可以连起来看：**越来越多过去依靠 prompt 和模型记忆维持的信息，正在被提升为可持久、可查询、可恢复的系统状态。**

**Worth reading:** 是。尤其适合关注 multi-agent workspace、代码 provenance、context lineage 与长期 Agent memory 的实现方式。

## Daily signal

今天三条信息分别落在模型、Harness 与持久状态三个层次，但方向一致：长期 Agent 的能力正在从“模型能持续生成多少轮”转向完整系统工程。

```text
Model capability / economics
        ↓
Long-running Agent
        ↓
Harness policy + recovery
        ↓
Durable state / provenance
        ↓
Auditable multi-agent collaboration
```

Fable 5.1 把 hours-long execution、failure recovery、self-verification 和 cache economics 拉进模型层竞争；Claude Code 2.1.257 把 auto mode 的安全边界扩展到 credential、network、workspace、MCP 与 plugin containment，同时继续完善后台任务和 subagent 恢复；Zed 则展示了代码 identity、causal history 与 structured thread 如何成为 Agent 可以直接消费的持久状态。
