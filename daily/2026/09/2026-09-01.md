# Agent 一手情报｜2026-09-01

本轮筛选出 3 条值得归档的新增信息。今天最清晰的技术信号不是新模型，而是 Harness 对“哪些状态必须由 runtime 保证”的边界继续外扩：Codex 开始把安全审查证据从模型可见的压缩历史中独立出来；Qwen Code 把多 Agent review fan-out 从模型需要严格遵守的 prompt 约定迁移为确定性的 workflow script；Claude Code 则继续处理远程控制、后台任务和权限持久化中的故障传播问题。

## OpenAI — Codex 0.152.0-alpha.7

- **Source:** OpenAI / Codex
- **Published:** 2026-08-31
- **Topics:** Context Engineering, Safety Runtime, Compaction, Token Budgeting, Guardian, MCP
- **Priority:** ★★★★☆
- **Original:** <https://github.com/openai/codex/releases/tag/rust-v0.152.0-alpha.7>
- **Compare:** <https://github.com/openai/codex/compare/rust-v0.152.0-alpha.4...rust-v0.152.0-alpha.7>
- **Status:** Alpha / pre-release

### What changed

0.152.0-alpha.7 延续了上一期 alpha 中的 runtime 治理方向，但本轮最值得关注的是 **Guardian review context 与普通模型上下文开始明确分层**。

官方 compare 中新增了一组相互关联的改动：

- Guardian review evidence 在 compaction 之后仍独立保留，不再完全依赖模型当前可见的 compacted conversation history；
- review history 采用有界、按时间顺序的独立保留，并对 user messages 与其他 transcript items 设置不同限制，避免大量 tool traffic 把用户指令挤出安全审查上下文；
- `request_user_input` 等可信用户回答可以跨 compaction / eviction 保留，但在 rollback 或 history reconstruction 后重置；
- 当用户消息中的图片超过 Guardian history budget 时，可以丢弃超大图片，但继续保留同一消息中的文本与 metadata；
- Guardian reviewer subthread 不再继承 history extension tools，缩小审查 Agent 的能力面；
- model metadata 新增默认启用 token budgeting 与 history-notes extension 的能力，在用户没有显式配置时可于 thread startup 激活；
- MCP server name 开始支持 `:`, `@`, `/`, `.` 等 package-style identifier，并在 CLI、runtime namespace 与 OAuth credential lookup 中保持一致。

### Technical details

这组变化把同一个 Agent session 中的上下文进一步拆成了职责不同的 context planes：

```text
Conversation / Model Context
        ↓
   compaction
        ↓
Compacted model-visible history

Safety / Guardian Context
        ↓
independent bounded retention
        ├─ protects user instructions from tool-noise eviction
        ├─ keeps trusted user answers across compaction
        ├─ may drop oversized media while retaining text
        └─ resets trust state on rollback / reconstruction
```

过去把 conversation history 视为唯一事实载体时，compaction 主要是 token optimization 问题；但一旦同一历史还承担 approval、Guardian review、permission reasoning 等安全职责，压缩就会改变审查证据本身。Codex 现在开始显式保留一份独立于模型压缩历史的 review evidence，并让不同来源的上下文拥有不同 retention / eviction 规则。

model metadata 能够在 thread startup 打开 token budgeting / history notes，也说明 context policy 正在从纯用户配置向 **model-aware runtime policy** 演进：不同模型可以声明适合自己的上下文预算与历史扩展策略，而 Harness 在 session 创建时完成激活。

### Why it matters

这里体现的核心变化是：**Context Engineering 开始同时承担推理效率与安全语义，二者不能再共享同一套压缩和淘汰策略。** 对长期 Agent 而言，未来更合理的 Harness 设计需要区分 model context、audit/review context、permission state、task state 等不同状态面，并分别定义 retention、trust、rollback 与 compaction 规则。

当前仍为 alpha，本条更适合作为架构信号观察；后续需要继续跟踪 0.152.0 stable 是否保留这些 Guardian / token-budgeting 语义。

**Worth reading:** 是。优先阅读 compare 中 Guardian history、token budget 与 MCP identifier 相关 commit，而不是只看 alpha release 页面。

## Qwen Code — 0.22.3-nightly.20260831

- **Source:** Qwen / Qwen Code
- **Published:** 2026-08-31
- **Topics:** Multi-Agent, Review Agent, Workflow Runtime, Orchestration, Resource Budget
- **Priority:** ★★★★☆
- **Original:** <https://github.com/QwenLM/qwen-code/releases/tag/v0.22.3-nightly.20260831.3a0c4c6108>
- **Key PR:** <https://github.com/QwenLM/qwen-code/pull/10119>
- **Status:** Nightly / pre-release

### What changed

本次 nightly 中最值得关注的是 Review Agent 新增 `qwen review emit-workflow`：它可以把 Review Step 3A 的完整多 Agent fan-out 生成为一个可执行 workflow script，而不是继续要求上层模型 orchestrator 在一次响应中严格复制并发 agent calls。

生成的 workflow 会固定使用既定 roster、review plan、brief、prompts 与 evidence，通过 runtime 的 `parallel()` 分发各个 reviewer，并把每个 reviewer 绑定到 review worktree、指定 review subagent type，同时检查缺失返回。生成脚本位于受信任的 generated-scripts root，可通过路径加载执行。

官方 PR 直接说明了改动动机：旧方案依赖模型遵守一组容易漂移的 orchestration convention，例如必须一次性发出全部 agent calls、prompt block 必须逐字保持、不能擅自缩减 reviewer roster；这些约束在真实运行中已经出现破坏。新的 emitter 把这些约束从模型行为迁移为文件和 runtime 的确定性属性。

该 workflow 还对超大 review fan-out 设置显式拒绝条件，因为当前所有 reviewer 结果最终仍会通过单个 Workflow tool result 返回；当 source / diff 规模过大时会触发 result budget truncation。当前该 emitter 仍处于独立评估阶段，Review Skill 尚未默认路由到它。

### Technical details

架构变化可以表示为：

```text
Old
Model orchestrator
    ↓
prompt conventions
    ↓
N parallel agent calls
    ├─ roster may drift
    ├─ prompt may mutate
    └─ fan-out may be incomplete

New
Review plan / roster
    ↓
deterministic workflow emitter
    ↓
generated executable script
    ↓
runtime parallel()
    ├─ fixed roster
    ├─ fixed prompts
    ├─ pinned worktree
    ├─ fixed subagent type
    └─ missing-return checks
```

这不是普通的“增加一个 workflow 命令”，而是在重新划分 LLM 与 runtime 的职责：模型仍负责理解 review task 和形成计划，但 **fan-out 的结构完整性、并发执行方式、agent identity 与 prompt fidelity 不再依赖模型每次都正确复现**。

显式的 diff/source size guard 也很重要，它承认 multi-agent orchestration 不只是“能否并发”，还受到 tool-result budget、聚合通道和上下文容量约束。fan-out width 与 aggregation budget 开始成为 runtime contract 的一部分。

### Why it matters

多 Agent 系统的一个常见失败点是把确定性的 orchestration invariant 写进 prompt，希望模型长期稳定遵守。Qwen Code 此次改动把 reviewer roster、并发调度、worktree 绑定、prompt fidelity 等约束搬到可执行 workflow 中，属于 **从 prompt-defined orchestration 向 runtime-defined orchestration** 的明确迁移。

这类设计会直接提高可重复性、可测试性和 failure diagnosis 能力，也让后续 approval、retry、timeout、budget 与 convergence policy 更容易在 runtime 层统一治理。

**Worth reading:** 是。PR #10119 比 nightly release notes 信息密度更高，值得阅读全文。

## Anthropic — Claude Code 2.1.252

- **Source:** Anthropic / Claude Code
- **Published:** 2026-08-31
- **Topics:** Long-Running Agents, Recovery, Remote Control, Background Tasks, Permissions, Context Safety
- **Priority:** ★★★★☆
- **Original:** <https://github.com/anthropics/claude-code/releases/tag/v2.1.252>
- **Status:** Stable

### What changed

Claude Code 2.1.252 主要是一组 failure-path 修复，但都集中在长期运行 Coding Agent 的控制面和故障隔离：

- 修复 Claude Desktop / VS Code 托管的 Remote Control session 在与 claude.ai 连接质量下降时，tool 已执行完成但 session 仍可能停顿数分钟的问题；
- 修复后台任务产生超大失败输出时，错误内容被继续带入会话并导致整个 conversation 超过 API request size limit 的问题，例如磁盘已满时 git 产生的大量错误；
- 修复项目尚无 `.claude/settings.local.json` 时，“always allow” 权限选择无法持久保存的问题；
- 修复部分 macOS 环境中 Bash command 因 task output swap / tasks directory moved or linked 而失败的问题。

### Technical details

这里涉及两个不同的 failure channel。

第一类是 control-plane degradation：remote session 的 tool execution 已完成，但上层连接退化导致 completion state 无法及时推进。修复后的目标是避免“执行面已经完成，控制面仍卡住”的状态长期占据 session。

第二类是 error-output amplification：后台任务失败产生的大量 stdout / stderr 如果未经边界控制进入 conversation，就会把底层系统故障放大为 context overflow，最终使整个 Agent 无法继续请求模型。

```text
Background task fails
      ↓
very large error output
      ↓
[old] append into conversation
      ↓
API request exceeds size limit
      ↓
whole Agent session fails

[new]
failure output is bounded / handled
      ↓
session remains recoverable
```

权限持久化修复则属于 policy-state durability：用户做出的“always allow”决定需要成为稳定的 project state，而不能因为配置文件尚未存在就丢失。

### Why it matters

这些修复共同指向 long-running agent reliability 的一个核心要求：**任务失败、网络退化和权限状态问题必须被限制在各自的 failure domain 内，不能向 conversation context 或整个 session 无界传播。** 对 Coding Agent 来说，真正的长期稳定性不仅取决于 task retry，还依赖错误输出有界、控制面可恢复、权限状态可持久化。

**Worth reading:** 是。Release notes 很短，可以直接阅读全文。
